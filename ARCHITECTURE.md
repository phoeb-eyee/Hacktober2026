# SkinSync — Architecture

## Overview

A two-app monorepo:

- **`frontend/`** — React 19 + TypeScript + Vite + Tailwind CSS. Owns the UI and the
  user's personal data (product inventory + routine) in `localStorage`, behind a
  swappable data-access interface (`src/lib/storage.ts`).
- **`backend/`** — Python + FastAPI + Pydantic. Owns the AI integration and all
  structured reference data and deterministic analysis logic.

## Data flow

```
Browser ── image ──▶ POST /api/scan ──▶ Gemma 4 (Gemini API) ──▶ validated ScanResult
                                                        │
                                     user reviews/corrects ─┘
Browser ──▶ GET /api/ingredients, /api/ingredients/{id} ──▶ curated JSON → Pydantic
Browser ──▶ POST /api/analyze (candidate + routine) ──▶ deterministic engine ──▶ AnalysisResult
```

## Gemma 4's role — what the model does vs. deterministic code

**Gemma 4 (hosted via the Gemini API, model `gemma-4-26b-a4b-it`) does exactly one
job:** multimodal image understanding — reading brand, product name, and ingredient
text off a photograph and returning it as structured JSON. It is called **only** in
`backend/app/services/gemma.py` (the `/api/scan` endpoint).

**Deterministic application code does everything else** — ingredient normalization,
interaction-rule evaluation, redundancy detection, routine placement, persistence,
and validation. The analysis engine (`backend/app/services/analysis.py`) **never
calls the model**, and the model **never invents evidence**. Model output is treated
as untrusted data: parsed, normalized, validated, and gated behind a user
confirmation step before anything is saved.

This is the core safety property: an "incompatibility" finding can only come from a
curated interaction record, never from the model's opinion.

## Components

- `frontend/src/context/DataContext.tsx` — products + routine (localStorage).
- `frontend/src/context/IngredientContext.tsx` — ingredient index + alias resolution.
- `frontend/src/lib/api.ts` — API client + request builder.
- `backend/app/services/gemma.py` — model integration + response parsing.
- `backend/app/services/ingredients.py` — knowledge-base access + name normalization.
- `backend/app/services/analysis.py` — compatibility/redundancy engine.
- `backend/app/data/ingredients.py` / `interactions.py` — curated reference data.

## Known limitations

- Model accuracy measured on **clean synthetic labels only**; real-photo OCR accuracy
  is not yet measured.
- Curated knowledge base is small (15 ingredients, 10 interactions) and mostly
  `provisional` pending formal review.
- Persistence is `localStorage` (single demo user, no authentication).
- Name normalization handles common names/aliases, not every INCI/trade-name variant.
- The `gemma-4-31b-it` model was flaky (500s) on the hosted API, so the default is
  `gemma-4-26b-a4b-it`.
- Educational only — not medical advice.

## Future improvements (separate from completed work)

- Real-photo model evaluation set.
- Expand the ingredient/interaction database with a review pipeline.
- Supabase/PostgreSQL persistence + user accounts.
- Barcode scanning and a product catalog.
- An optional natural-language summary generated by Gemma 4, grounded strictly in the
  deterministic findings (never replacing them).
- Concentration-aware reasoning when a label states a percentage.

## Security

- `GOOGLE_API_KEY` lives in gitignored `backend/.env`, server-side only.
- Upload type + size validation; CORS restricted to the dev origin.
- No personal information is logged.
